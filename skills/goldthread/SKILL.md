# GoldThread：按目标迭代数据集

**本轮要让学生在哪类任务上做对什么？用什么证据判断？** 先回答这两个问题，再决定是否改数据。产出更多样本、让轨迹更短、生成新 ZIP，都不是优化目标。

## 开轮：接手目标，不接手上一模型的猜测

写一行任务卡：**目标行为｜基线（首版写“无父包”，迭代写父包和学生运行版本）｜证据来源｜不入训的留出任务与成功标准**。用 `python gt.py inspect graph --json` 和 `python gt.py inspect config --json` 确认当前工作区、版本关系和有效配置。基线不明或日志对不上，只做诊断，不发布。

- **首版教师数据**：选有原始任务、关键操作和可核验结果的示范。保留用户约束；教师是谁、用了多少步，都不是成功证据。
- **学生反馈迭代**：用 `gt eval student` 找异常，再回看学生和教师的实际交付物。例如，同样只走了三步，结果已验收是高效，承诺“稍后完成”却无交付才是早停。先排除工具、环境或预算差异，再决定是否需要训练样本。留出任务及近重复不参与策展。

## 改数据：每个决定都能回到当时的证据

1. **先试审，再批量改。** 接手的模型先选少量有代表性的案例，至少包括一条“不应改”的反例。逐条写清 `sid / msg_id 或 sample_id → 原始回执 → 改或不改及理由`。涉及批量删除、改写关键判断或偏好方向有争议时，先交另一位审核者复核；证据不足就保留、停用监督或暂停，不用猜测补齐。
2. **黄金步要忠实，不是事后写一个完美答案。** 用 `gt inspect session` 看上下文、`gt inspect step` 对照原始步。可以去重复，不能把后面才知道的结果写进前面的判断。能帮助诊断的失败要保留；折叠操作必须有成功回执，且能无歧义地重建完整改动。
3. **DPO 审的是同一上下文里的真实偏好。** 从 `/api/dataset/draft?kind=dpo` 分页列全候选，按真实 `sample_id` 到 `/api/dataset/draft/sample` 看完整上下文及两侧正文。按原始方向判 `good / swap / drop`，注意详情可能已展示对调后的顺序。正文变了，即使 ID 不变也要重审；不批量判好，不把“来自学生”当作负例理由。

**操作边界：** `gt` 指 `python gt.py`。数据变更只走 `gt curate` 等仓库原语，写明 `--reason`，用 `--json` 核对实际影响；不直接修改 `data/`、原始日志或冻结包。主链不需要外部模型，`gt assist` 仅作显式辅助，不能代替裁决。参数按需查 `python gt.py <子命令> --help`。

## 验收：数据可交付 ≠ 学生已提升

- **数据验收**：运行 `gt build --require-reviewed-dpo --reason "…" --json`。只有 raw 时，严格构建可先生成黄金层；若阻于待审 DPO，就复核、重试，不取消严格选项。确认退出码为 0、`gate.passed == true`，并核对预期样本、偏好方向及 train/eval 切分。按返回的 `build_id` 执行 `gt pack --build <build_id>`，选与学生匹配的 profile；迭代版用 `--parent` 绑定已核实的父包。快照保存在 `04_release/cas/`。对**实际下发的 ZIP** 执行 `gt gate check <zip_path> --json`，通过才交付，不用 `latest` 代替。
- **效果验收**：`gt eval diff` 只说明数据改了什么。新旧学生须在相同训练设置、同一批独立留出任务、相同工具权限、预算和评分标准下比较；既报目标行为，也报退步案例。没有重训和复测，就写 **“数据包已验收，学生效果未验证”**。
- **换模型交接**：用 `gt report publish` 归档目标、父包/新包标识、代表性证据、门禁与实测结果、未决项和下一步。下一位从报告和 `gt ledger list` 接手，不依赖聊天记录。若没有值得写入的数据，报告“不改”及理由，也是合格结果。
